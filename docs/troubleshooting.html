FOAM FATAL ERRORs

STARTUPUnknown fileOperationInitialise type uncollated

Full error text typically looks like:

FOAM FATAL ERROR:
Unknown fileOperationInitialise type uncollated
Valid fileOperationInitialise types are:
(
    dummy
)

Cause: The vendored simpleFoamExtracted binary was linked against a stripped-down build of libOpenFOAM that does not include the uncollatedFileOperation class (or its MPI-aware sibling masterUncollated). The FOAM_FILEHANDLER environment variable or the OptimisationSwitches block in etc/controlDict is requesting a handler that was compiled out.

Fix 1 — unset the environment variable: 
unset FOAM_FILEHANDLER
Fix 2 — override at runtime: 
simpleFoamExtracted -fileHandler uncollated

If neither works, the of_os (OSspecific) shared library was not built with fileOperation support. Rebuild with the full CMake target:

cmake --build build --target of_os
Fix 3 — check LD_LIBRARY_PATH:

Make sure libOpenFOAM.so from the vendored build is the first one found, not a system OpenFOAM installation:

ldd $(which simpleFoamExtracted) | grep OpenFOAM

STARTUPUnknown functionEntry 'includeFunc'

FOAM FATAL ERROR:
Unknown functionEntry 'includeFunc'
Valid functionEntry types:
(
    calc
    code
    codeStream
    include
)

Cause: includeFunc is a macro that expands to a path in $FOAM_ETC/caseDicts/postProcessing/. It requires the full OpenFOAM installation with its function-object dictionaries on disk. simpleFoamExtracted is a vendored binary that does not bundle those data files, so the entry cannot be resolved.

Fix — remove all includeFunc lines from system/controlDict: 
// REMOVE lines like these from functions{}:
//   #includeFunc  residuals
//   #includeFunc  streamlines

// Replace with an empty block:
functions {};

If you need residual monitoring, parse the log file with the provided residuals_analysis notebook instead.

STARTUPUnknown function type streamlines

FOAM FATAL ERROR:
Unknown functionObject type streamlines
Valid functionObject types:
(
    ...
)

Cause: The streamlines function object lives in libsampling.so, which is not linked into simpleFoamExtracted. The same applies to probes, surfaces, sets, and other post-processing function objects that depend on the sampling library.

Fix — remove the entry from system/controlDict: 
// Remove the entire streamlines sub-dictionary:
// streamlines
// {
//     type        streamlines;
//     ...
// }

functions {};

Post-processing of velocity streamlines can be done entirely inside ParaView (Filters → Stream Tracer) after the run completes — no in-solver function object is needed.

DIVERGENCESIMPLE solution diverged

SIMPLE solution diverged after 47 iterations
ExecutionTime = 12.3 s  ClockTime = 12 s

Cause: The SIMPLE iteration became unstable. This can happen for several reasons: under-relaxation factors too high, poor initial conditions, a bad mesh (high non-orthogonality or skewness), or an aggressive numerical scheme on a coarse mesh.

Primary fix — reduce relaxation factors in system/fvSolution: 
relaxationFactors
{
    fields      { p  0.2; }         // was 0.3
    equations
    {
        U       0.5;                // was 0.7
        k       0.5;
        epsilon 0.4;                // epsilon often needs the most damping
    }
}
Secondary fixes:
  • Switch convection scheme to pure upwind in system/fvSchemes: div(phi,U) bounded Gauss upwind; — first order but very robust.
  • Start from a better initial condition: run a few iterations with laminar settings, then switch to turbulent.
  • Increase nNonOrthogonalCorrectors to 2–3 in SIMPLE{} if mesh non-orthogonality exceeds 70°.
  • Check that boundary conditions are consistent (e.g., the pressure reference is set at exactly one patch — not zero patches or two).

CONVERGENCEMaximum number of iterations exceeded

GAMG:  Solving for p, Initial residual = 0.812, Final residual = 0.731,
       No Iterations 1000
FOAM Warning: Maximum number of iterations exceeded

Cause: The linear solver for the pressure (or another field) failed to reduce the residual to the requested tolerance within the iteration limit. This is almost always a mesh quality problem or a misconfigured solver.

Fix 1 — run checkMesh and address quality issues: 
checkMesh

Look for:

MetricAcceptableAction if exceeded
Max non-orthogonality< 70°Increase nNonOrthogonalCorrectors
Max skewness< 4Remesh or use skewness corrected schemes
Max aspect ratio< 1000Reduce grading, especially near walls
Fix 2 — relax the inner solver tolerance: 
// In fvSolution solvers{} for p:
relTol   0.05;   // allow early exit relative to initial residual
tolerance 1e-5;  // don't demand more precision than needed
Fix 3 — switch p solver to PCG for highly non-orthogonal meshes: 
p
{
    solver          PCG;
    preconditioner  DIC;
    tolerance       1e-6;
    relTol          0.05;
}

CRASHFloating point exception

FOAM FATAL ERROR: floating point exception
Foam::sigFpe::sigFpeHandler(int)
...
[stack trace follows]

Cause: A NaN or Inf propagated into a field — typically caused by one of: (a) bad initial conditions that produce negative k or epsilon, (b) a cell with near-zero or negative volume from the mesh, or (c) a physically impossible boundary condition (e.g., negative inlet k).

Fix 1 — check initial conditions are physically valid: 
// k must be > 0 everywhere
// epsilon must be > 0 everywhere
// U should be a reasonable non-zero field if using turbulent BCs

// Quick sanity: k = 1.5*(I*Uref)^2, I=0.05, Uref=1 m/s
// k = 1.5 * (0.05)^2 = 3.75e-3  (OK)
// epsilon = Cmu^0.75 * k^1.5 / L,  L~0.07  =>  ~7e-4  (OK)
Fix 2 — check the mesh for zero-volume or negative-volume cells: 
checkMesh
// Look for: "FOAM FATAL ERROR: face ... has zero area"
// or:       "Negative cell volumes"
Fix 3 — enable bounds checking in system/fvSolution: 
// Add to SIMPLE{} to clip k and epsilon to positive values:
SIMPLE
{
    ...
}
// or add to the field solver:
k       { solver smoothSolver; ... minIter 1; }
// Set field limits in 0/k:
// bounds  ( 1e-15  1e+8 );
Fix 4 — reduce relaxation factors dramatically as a diagnostic step: 
relaxationFactors { fields { p 0.1; } equations { U 0.3; k 0.3; epsilon 0.2; } }
Warning: if the FPE occurs on iteration 1, the problem is almost always in the initial conditions or the mesh, not in the relaxation. Fix those first.

PARALLELMPI_ABORT called in parallel run

FOAM FATAL ERROR (on master):
decomposition of mesh does not match number of processors
nProcs = 4  nDomains = 6

[mpirun] MPI_ABORT was invoked ...
aborting MPI_COMM_WORLD (comm=0x44000000), error 1

Cause: A mismatch between the number of MPI ranks requested (mpirun -np N) and the number of subdomains defined in system/decomposeParDict (the numberOfSubdomains key). Both must be identical.

Fix — synchronise decomposeParDict and -np: 
// system/decomposeParDict
numberOfSubdomains  4;          // must equal -np value
method              scotch;     // or simple / hierarchical

// Run command must match:
mpirun -np 4 simpleFoamExtracted -parallel
Other common parallel errors and their causes:
ErrorLikely cause
Cannot open file "processor0/..."decomposePar was not run, or was run with different -np
Pstream::init: MPI_Init returns errorMPI runtime not installed or libmpi.so not in LD_LIBRARY_PATH
Hang at startup with no outputFirewall blocking MPI inter-process communication on localhost
inconsistent patch sizesOld processor*/ directories from a previous decomposition — delete and re-run decomposePar
Clean parallel directories before redecomposing: 
rm -rf processor*
decomposePar
mpirun -np 4 simpleFoamExtracted -parallel 2>&1 | tee log.txt

General debugging tips

1. Check residuals first

Before guessing at the cause of a failure, plot the residuals. A sudden jump to NaN points to a physical/mesh problem; a slow plateau that never drops points to a solver configuration issue. 

# Quick grep to see worst residuals per field:
grep "Initial residual" log.txt | awk '{print $NF, $0}' | sort -n | tail -20

For a full time-series plot, use the residuals_analysis notebook.

2. Validate mesh quality with checkMesh

checkMesh 2>&1 | tee log.checkMesh

Key numbers to watch:

MetricTargetHard limit
Max non-orthogonality< 50°70° (above: add correctors)
Average non-orthogonality< 20°40°
Max skewness< 24 (above: likely divergence)
Minimum face area> 0Must be positive
Minimum cell volume> 0Must be positive

3. Start simple, increase complexity

If a case won't converge, strip it down: switch to laminar (simulationType laminar), use pure upwind schemes, and halve all relaxation factors. Once that converges, reintroduce turbulence and better schemes one at a time.

4. Use foamLog to extract residuals (if full OF is available)

foamLog log.txt
# writes logs/Ux_0, logs/p_0, etc. — tab-separated time/residual pairs

5. Inspect the first iteration in detail

Set endTime 1 in controlDict and writeInterval 1. Then load the single time-step in ParaView and check for obvious anomalies (reversed flow, pressure oscillations, negative k) before running to convergence.
